# RZ-41: Crypt encrypt-then-MAC, unique ORM placeholders, no raw Where operands

## Security
- `Crypt` writes a new versioned format (v2): `0x02` · IV (16) · ciphertext · HMAC-SHA256 (32).
  The HMAC now covers version + IV + ciphertext, so an IV bit flip (which changed the first
  plaintext block and still passed the old MAC) fails. The HMAC is checked with `hash_equals`
  **before** anything is decrypted. AES and HMAC use separate keys derived from the one secret
  with HKDF-SHA256 (info `razy-crypt-v2-aes-256-cbc` / `razy-crypt-v2-hmac-sha256`); the secret
  is no longer used directly by either. Hex input must be of even length.
- `WhereSyntax`: an operand that is none of the recognised forms used to go into the SQL text
  verbatim (`id=SLEEP(5)`, `a=b+1`, `meta~=x y`, `email#=^a.*`, `>id+1` in `order()`). It now
  throws `Razy\Exception\InvalidOperandException` (extends `QueryException`; the operand is in
  `getOperand()`, kept out of the message). Still accepted, each pinned by a test: numbers
  (`1`, `-2`, `3.5`, `.5`, `1e3`), bare identifiers and keywords in any case (`UserId`, `T.b`,
  `TRUE`, emitted unquoted as before) and zero-argument functions in
  `WhereSyntax::SQL_FUNCTIONS` (`NOW()`, `CURRENT_TIMESTAMP`, `RAND()`, ...). The right side of
  `*=` `^=` `$=` `@=` was always bound as a value and still accepts unquoted text. A quoted
  literal with an escaped quote (`'O''Brien'`, `'O\'Brien'`) used to reach the SQL raw; it is
  now decoded and bound like any other quoted text.
- `WhereSyntax`: a stray closing parenthesis (`id=:id)--`) made the tokenizer drop the whole
  condition, so the statement ran with **no WHERE**: `delete('t', ['id' => 1], 'id=:id)--')`
  ran `DELETE FROM t`. It now throws `QueryException` ("unbalanced parenthesis"). A group glued
  to an expression (`NOW()(...)`) is a `QueryException` instead of a `TypeError`.

- `WhereSyntax`: a JSON path (`col->'$.a'`) was appended as written. SQLite and Postgres do
  not treat `\'` as an escape, so `delete('t', ['id' => 1], "id->'$.a\' OR 1=1 --'")` ran with
  `OR 1=1` and deleted every row. The path is now re-quoted by the driver (`PDO::quote`), and a
  path holding its own quote character or a backslash throws `InvalidOperandException`.
- `ORM\ModelQuery` helpers (`whereIn`, `whereNotIn`, `whereBetween`, `whereNotBetween`,
  `whereNull`, `whereNotNull`) take one identifier (`col` or `t.col`); the column was spliced
  into Simple Syntax (`whereIn('1=1|id', [0])`). Their bindings use the reserved prefix
  `_mq_`, which `where()` / `orWhere()` refuse, and are written after the `where()` bindings:
  a `where()` parameter named after a helper's key (`_wi_category` before this release)
  replaced the helper's values.
- `ORM\ModelQuery::bulkUpdate()` keys must be column names; a key was Update Simple Syntax,
  so `['name=(SELECT ...)' => 'x']` ran the subquery.
- Update Simple Syntax (`Statement::update()`): a SET token that is not `?`, `:name`, quoted
  text (now bound) or a Where raw-safe operand (number, identifier, allow-listed zero-argument
  function) used to be pasted as written (`name=(SELECT ...)`, `n=SLEEP(5)`); it now throws
  `InvalidOperandException`. An entry that is not `col`, `col++`, `col=value` or `col+=value`
  is a `QueryException` instead of being skipped silently.
- `WhereSyntax`: an array literal (`[1,2]`) kept its text as SQL when it stood alone, on the
  left of a comparison, or inside a JSON operator (`meta~=["a') OR 1=1 --"]` pasted the JSON;
  on SQLite `[...]` is identifier quoting). A lone or left-hand array now throws
  `InvalidOperandException`; in JSON operators the array is bound (`CAST(:p AS JSON)`), which
  also makes `col~=[1]` valid on MySQL. Right-hand arrays for `IN` / `BETWEEN` are unchanged.
- `JOIN ... USING` (`[:col1,col2]` in `from()`): the columns were concatenated as written
  (`[:id); DROP TABLE t--]`); they are now validated and quoted like the `ON` form.

## Fixed
- `ORM\ModelQuery`: `whereIn`, `whereNotIn`, `whereBetween`, `whereNotBetween`, `whereNull` and
  `whereNotNull` built their placeholder from the column name, so a second call on the same
  column overwrote the first call's values (`whereIn('c', [a, b])->whereIn('c', [b, d])` ran
  `c IN (b, d) AND c IN (b, d)`). Each call now gets its own placeholder (`_mq_wi_1`, ...).

## Changed
- `Crypt::decrypt()` returns `?string`: `null` on tampering, a wrong key or malformed input,
  so a failure is no longer the same value as an empty plaintext (`''`).
- `Crypt::decrypt(..., bool $allowLegacy = false)` refuses the legacy format unless the caller
  opts in for migration.

## Added
- `Crypt::needsReencrypt(string $encryptedText, string $key): bool` — true when a value opens
  only through the legacy format.
- `Crypt::VERSION`, `WhereSyntax::REGEX_NUMBER`, `REGEX_IDENTIFIER`, `SQL_FUNCTIONS`,
  `WhereSyntax::isRawSafeOperand()`, `WhereSyntax::decodeQuoted()`.

## Deprecated
- The pre-RZ-41 Crypt format (IV · HMAC(ciphertext) · ciphertext, one key). `decrypt()` refuses
  it by default; `decrypt($value, $key, allowLegacy: true)` reads it, read-only and
  verify-first, for migration only. **A legacy MAC does not cover the first block, so
  re-encryption does not prove integrity**: an IV bit flip changes the first plaintext block
  and still passes, and re-encrypting seals the changed value. **Removed in v2.0.0**: before
  upgrading, re-encrypt every stored value for which `needsReencrypt()` is true. Values written
  by older releases cannot be read after that.

## Compatibility
- `Crypt::decrypt()` failure is `null`, not `''`: replace `=== ''` checks with `=== null`;
  `?: ''` and `?? ''` keep working. Reading values written before this release needs
  `allowLegacy: true` (migration only).
- Update Simple Syntax values outside the operand list, and unparseable `update()` entries,
  now throw. A ModelQuery helper column that is not one identifier throws.
- Values written by `Crypt::encrypt()` from this release on cannot be read by older releases
  (roll back only with values written before the upgrade, or re-encrypt).
- A Where syntax string with an operand outside the list above now throws where it used to
  emit that text into the SQL. Bind the value (`:name` + `assign()`) instead. A function with
  arguments, arithmetic and `0x` literals are among the refused forms.
- Code that read ModelQuery's internal placeholder names (`_wi_<column>`, `_wb_<column>`)
  must not; they were never API.
