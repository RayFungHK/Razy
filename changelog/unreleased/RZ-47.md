# RZ-47: security follow-ups of RZ-41

## Security
- `SimpleSyntax::parseParens()` throws `Razy\Exception\SyntaxException` on a stray `)` or an unclosed `(`. Before, a
  stray `)` silently dropped everything parsed so far and an unclosed `(` was read as if closed. The query builder
  turns it into a `QueryException` for Where, ORDER BY (`order('>id)--')` used to drop the whole ORDER BY), Update
  Simple Syntax and JOIN syntax; `WhereSyntax::VerifySyntax()` reports it as invalid (`''`). Version ranges
  (`VersionUtil`) and template `{@if}` conditions, both developer-written, now fail loud with `SyntaxException`.
- `Statement::order()`: a parenthesised group as a sort key is a `QueryException` (was a `TypeError`).
- `ModelQuery::bulkUpdate()`: each SET value is bound to its own reserved placeholder (`_mq_set_N`). Bound as
  `:column`, a `where()` parameter of the same name replaced the value being written.
- A JSON path containing a NUL byte is refused (`PDO::quote()` truncates at NUL).
- `ParameterBinder::paramsUsedIn()` counts `:rzpN` only outside comments (`/* */`, `--`), quoted literals and
  quoted identifiers; PDO skips those, so a placeholder-like text inside `'...'` bound a value with no placeholder.
  Comments are scanned as their own spans, as PDO does: a quote inside `/* ' */` no longer pairs with a later
  literal and drops the live placeholders between them (SQLite then ran them as NULL).
- `Model::firstOrCreate()` / `firstOrNew()` / `updateOrCreate()` (via `firstByAttributes()`) and
  `Model::increment()` / `decrement()` validate the keys / column they splice into Simple Syntax as single
  identifiers (`QueryException` otherwise).

- A `"0"` token is a condition or a value, never "nothing": `SimpleSyntax::parseParens()`, the Where / Update / JOIN
  token loops and the SELECT / UPDATE / DELETE builders tested strings for truthiness, and `"0"` is falsy in PHP.
  `where('0')` ("match nothing") compiled to no WHERE at all, so `delete($table, $params)->where('0')` emptied the
  table and `update()->where('0')` wrote every row; `where('id=1,0')` left a dangling `AND`, `SET price=0` had no
  value. `Database::delete($t, $params, '0')` and `ModelQuery::bulkDelete()` with `where('0', $params)` no longer
  replace the "0" with a WHERE built from the params. An empty group (`where('id=1,()')`) is now a `QueryException`; it used to drop the rest of the condition.

## Changed
- `Crypt::encrypt()` / `decrypt()` / `needsReencrypt()` throw `InvalidArgumentException` for an empty key; it was
  aliased to `"\0"`, which protects nothing.

## Compatibility
- A syntax string with unbalanced parentheses throws where it used to be silently rewritten. A caller relying on
  an empty Crypt key must pass a real secret.

### Migrating records encrypted with an empty key
Records written with `""` can no longer be opened with `""`. They still open with the key `"\0"`, in both formats:
the v2 format derived its keys from `"\0"` when given `""`, and the legacy format's HMAC and AES both zero-pad a
short key. Re-encrypt them once with a real secret, before or after upgrading:

```php
$plain = Crypt::decrypt($stored, "\0", allowLegacy: true);   // allowLegacy only if pre-RZ-41 records exist
if ($plain !== null) {
    // check $plain before trusting it (see below), then:
    $stored = Crypt::encrypt($plain, $realSecret, true);
}
```

- Use `"\0"` only in that one-off migration script, never as a standing key: like `""`, it protects nothing.
- Treat every recovered plaintext as untrusted input. Anyone could have written a record under an empty key, and
  the legacy MAC does not cover the IV, so its first 16-byte block can be altered without detection.
- `Crypt::needsReencrypt($stored, "\0")` finds the legacy ones.
