# RZ-52b: embedding API (boot a distributor from your own script)

(TASKFLOW line 656; the id `RZ-52` is also the older "0 token" fix, so this file is `RZ-52b`.)

## Added
- `Razy\Embed::boot(string $root, string $dist): Distributor`: the documented entry for a process that is not the web front controller or the `Razy.phar` command line. It checks the root and `sites/<dist>/dist.php`, defines `SYSTEM_ROOT` and the path constants, loads the bootstrap `main.php` loads, and returns an initialised Distributor. Load it by `phar://<file>/library/Razy/Embed.php` or composer's autoloader; requiring `Razy.phar` itself runs the CLI dispatcher. A second call with the same root is allowed; a different root in one process throws `ConfigurationException`. A rejected argument throws before anything is defined; once `dist.php` is accepted, an exception from the Distributor leaves the constants and the bootstrap in place and the root fixed. `boot()` installs the bootstrap's exception handler and does not chain the host's. Manual: `manual/06-packages-and-deployment.md` §6.
- `Application::getDistributor(string $code): ?Distributor`: the initialised Distributor for a `hasDistributor()` key (`code` or `code@tag`) mounted on the host `host()` matched, or null.
- `Config\SiteConfig::parseIdentifier(string): ?array`: the one parse of `code[@tag]` into `[code, tag]` (`*` when untagged).

## Fixed
- `php Razy.phar bridge` works. It called `Application::getDistributor()`, which did not exist (`{"ok":false,"error":"Call to undefined method Razy\\Application::getDistributor()"}`). It now answers with the typed outcome of `executeInternalChecked()`: `{"ok":true,"data":…}` (a handler that returns null is `ok` with `data` null), `{"ok":false,"status":"unknown"|"failed","error":"…"}` for a command that is not registered or threw. The message and trace of a failing command are not on stdout (the trace goes to stderr). Exit code unchanged.
- A Distributor built without a Domain (`runapp`, `Embed::boot()`, the compile and package tools) registers its own module library autoloader in `initialize()`, once per Distributor. A module command that used a class from the module's `library/` folder failed with `Class "..." not found` on that path; only `Application::host()` registered an autoloader.
- `php Razy.phar build` run from a folder that has no `sites/` and is not the phar's folder installed Razy next to the phar. It now prints an error, exits 1 and writes nothing.
- A tagged dist identifier `code@tag` was split with `explode('@', $id . '@', 2)`, which makes `demo@dev` code `demo`, tag `dev@`: the tag's module pins were not applied and the `*` set loaded, silently. `Domain::matchQuery()`, `Domain::dispatchQuery()`, `Application::updateSites()`, `runapp` and `Embed::boot()` now share `SiteConfig::parseIdentifier()`.

## Compatibility
- **A tagged lookup now loads the tagged set.** A sites key `code@tag` (and `php Razy.phar runapp code@tag`) used to run with the tag `tag@`, so a dist.php `modules` pin for `tag` was ignored and the `*` set loaded; it now loads the pins for `tag`. A site that relied on the old (wrong) result sees different module versions: check the `modules` entries of tagged dists. `runapp code@` (a trailing `@` with no tag) is now refused as an invalid identifier.
- **The local bridge is usable, and it is not gated.** Before this PR `php Razy.phar bridge` crashed before running any command, so nothing ran through it. It now runs the command. The `bridge` CLI is local shell trust: it consults neither `__onAPICall` nor `__onBridgeCall` nor `RAZY_BRIDGE_SECRET` (those apply to `executeBridgeCommand`). Whoever may run it may call every API command of the distributor.
- `build` from a folder without `sites/` (or `standalone/`) and not the phar's own folder used to install into the phar's folder; it now exits 1. Running `build` in the phar's own folder, or in a folder that has `sites/`, is unchanged.
- A Distributor with no Domain now registers an autoloader in `initialize()`. Code that registered `spl_autoload_register(fn ($c) => $dist->autoload($c))` itself for such a Distributor (`Testing\Client`, `Package\PackageRunner`) keeps working: the second autoloader is only asked for a class the first did not load. The registration holds the Distributor weakly and is removed when the Distributor is destroyed (a closure that holds the Distributor strongly, as `PackageRunner`'s does, keeps it alive, and so keeps this registration). Distributors built by `Domain` (the web and worker path) add none.
- No existing method changed; `Distributor::autoload()` and the Application autoloader are as before.
