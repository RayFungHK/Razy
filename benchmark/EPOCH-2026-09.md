## Honest reads of the tables

- The FPM table, stated with its grain: at 200 VUs Razy's plain-FPM deployment
  runs at ~0.32× Laravel's (static 295 vs 921 RPS; both sides' averages of
  344/96 ms are queue-depth phenomena at 200 VUs/32 workers, not per-request
  cost — a sequential single request measures sub-millisecond on both). The
  cheap suspects were executed and cleared: phar signature verification is
  2.2 ms per fresh `loadPhar` (measured in-container), and after the `chown`
  fix the cache tree is writable. Laravel's cheaper cold boot has a named
  architectural cause — `config:cache`/`route:cache`/`view:cache` compile the
  framework to static arrays at deploy; Razy assembles at boot. A full
  flamegraph attribution of Razy's boot under concurrency was left OPEN by this
  epoch (an unproven cause is not published) — and CLOSED two days later below. The worker table is the
  framework-vs-framework number; the FPM table plus the gain tables show each
  stack's home ground: Razy 21–30× worker-over-FPM on request-shaped scenarios
  (4.4× write-bound, 1.8× CPU-bound), Laravel 1.75–3.1× (and 0.5×
  on heavy CPU — frankenphp's threads-vs-processes grain, running honest).

- The worker table is the only framework-vs-framework number: identical PHP,
  identical server, identical runtime policy on both sides.
- The fpm table shows what the frameworks cost when every request boots from
  cold; worker-mode gain is then per-stack, stated, not assumed.
- DB write is MySQL-bound on both stacks — the tables should (and do) land

- The 02/05 deltas vs the 2026-02 table are the expected cost of honesty: the

## Invalid-pass log (kept, not hidden)

The first `razy-fpm` pass produced Razy fpm at 0.17–0.41× with 1–3 second p95 —
too catastrophic to be believable, and it wasn't: the image's runtime cache tree
(`/app/site/data/cache`) was root-owned while the fpm pool ran as `www-data`, so
every template re-compiled and every cache write silently failed. The Laravel fpm
image has always carried the matching `chown` (`/app/storage`) — its first-pass
numbers were audited for the same class of defect, found clean, and RETAINED.
The Razy image gained `chown -R www-data /app/site`, its invalid raw JSON was
deleted, and only that one pass was re-run (passes are serial and independent;
the other three stacks' data was collected under fair conditions).

## Scenarios 07–10 — the v1.1 readiness-gate curve (2026-09-17, same machine, serial)

The gate scenarios landed as promised: `benchmark/gate/` builds a FULL dist site
(`benchgate`: dist.php + version-dir modules, modern anonymous-class controllers) on the
same FrankenPHP 1.10 worker, hosting four honest shapes served by ONE process:

| module | gate shape | honest answer |
|---|---|---|
| `bench/gate-ready` | migration declared + applied at deploy (entry `migrate`) | 200 `ok` (memo-hot) |
| `bench/gate-vacuous` | nothing declared — the common case | 200 `ok` (vacuous, no DB ever) |
| `bench/gate-refused` | migration declared, never applied (staged post-migrate) | 503 naming module + command |
| `bench/plain-plain` | IDENTICAL handler, NO gate | 200 `ok` — the control |

| scenario | RPS | p95 ms | avg ms | checks |
|---|---|---|---|---|
| 07 gated-ready | 8,558 | 2.79 | 1.17 | 100% (200+`ok`) |
| 08 gated-vacuous | 8,564 | 2.78 | 1.17 | 100% |

**Reads (honest):**
- Gate tax (07−09b): **+0.2% RPS — inside run-to-run noise** (spread within each

- Vacuous case (08) equals the ungated control exactly — the no-migration default is free.
- The honest 503 path (09) costs +0.09 ms avg (~7% of a 1.2 ms request) — refusal at

### Scenario 10 — module-scale boot curve (5/25/50 modules, 3 rounds each)

`benchmark/gate/boot-curve.sh` (k6 cannot measure this): cold `up`, poll to first 200,
three follow-up latencies, container RSS. SCALE is a build-arg on the same Dockerfile.

| modules | boot→first-200 (median) | cold req1 | warm req | RSS |
|---|---|---|---|---|
| 5 | 1,363 ms | 4.9 ms | ~3.4 ms | ~141 MiB |
| 25 | 1,436 ms | 7.1 ms | ~3.6 ms | ~141 MiB |
| 50 | 1,415 ms | 7.8 ms | ~3.4 ms | ~142 MiB |

**Read:** boot is FLAT in module count within the measured band (±5% noise), RSS flat,
cold first-request +~3 ms at 50 modules (scanner/dispatch first-touch, one-time). Boot
here is dominated by Caddy+PHP worker pool startup + entry migrate-probe, NOT by module
count — the honest statement is "5→50 modules costs nothing measurable to boot on this
runtime"; beyond 50 is unexplored territory, NOT extrapolatable. Raw:
`benchmark/results/gate/boot-curve-2026-09.txt`.

### Two framework defects this suite caught by existing (both fixed, changelog `[Unreleased]`)

1. **No multisite site could EVER boot under worker mode** — the boot pass has no
   request, HOSTNAME sits at its `'UNKNOWN'` sentinel, and the worker branch fed it to
   `host()` FQDN validation; every thread died and Caddy panicked the pool. The
   standalone path had masked this everywhere. Boot now resolves the sentinel to the
   documented `'*'` default site. Pin: `tests/WorkerBootHostTest.php`.
2. **The `'*'` default site was unreachable by construction** — `matchDomain()` ends with
   a documented `'*'` fallback but `updateSites()` validated every key through `isFqdn()`
   (2+ char label grammar), so `'*'` never entered the table the fallback reads.
   Behavioral fixture: `tests/DefaultSiteTest.php`. (Adjacent doc-trap — the stock
   sites.inc.php comment advertised a string shortcut no parser reads — fixed in the
   setup template the same week.)

The gate suite exists precisely because a gate that is never measured is a gate nobody
trusts; it paid for itself before the first load was even run.


## FPM cold-boot attribution — the OPEN item, CLOSED (2026-09-17)

Method and honest trail first: an xdebug profile pass produced numbers that
CONTRADICTED the published tables (a no-sleep probe showed Razy 7.5k RPS; the
official ramp profile shows 294). The contradiction was chased down instead of
papered over: **xdebug's profile mode writes a cachegrind file per request**, and
that per-request file IO — whose cost scales with the instructions profiled, i.e.
massively asymmetric between the two stacks — invalidated every fpm number taken
while it was on, in BOTH directions. Those probes are named here and shipped as
INVALID; the files were deleted from the containers. With xdebug fully removed
(conf file deleted, pool reloaded):

- **Reproduction:** controlled re-runs of scenario 01 land at Razy 229 / Laravel 850
  (`results/recheck/01_razyfpm_clean.json`, `01_laravelfpm_clean.json`) — the
  published 294.6 / 921 reproduced at the same 0.27x ratio (78–92% level, same
  direction). The published FPM table stands; yesterday's pass was NOT contaminated.
- **The bottleneck is CPU, not queueing** (the two possible causes, now separated).
  CORRECTION, published against myself (the law: invalidated passes are logged
  publicly): the first saturation evidence quoted here — "no-sleep probes: Razy
  9,187 RPS vs Laravel 27,488 → 0.21 vs 0.07 ms CPU/request" — is **INVALID**.
  Those ad-hoc k6 probes ran with `noThresholds` and ZERO checks, so pool-overflow
  502s were counted as `http_reqs`: the RPS was inflated on BOTH sides by an
  unmeasured 502 share, and any ms-CPU/request divided from it inherits the lie.
  The cgroup reading that survives from the same pass is the qualitative one
  (both containers pinned at the 2-core quota — CPU-bound, not queue-bound; that
  holds even in a 502 storm because the CPU is real work either way). The honest
  math comes from the CLEAN CHECKED re-runs above, which plateau at the same
  2-core cgroup quota by the official profile's own design: CPU/request under
  saturation ≈ 2 cores ÷ RPS ⇒ **Razy ≈ 8.7 ms vs Laravel ≈ 2.35 ms**, a ~3.7x
  CPU-cost gap — same direction as the published 0.27x throughput ratio, now
  divided only from numbers that carry checks. (Pools verified symmetric:
  `pm = static`, 32 children, identical `benchmark.ini` both images.)
- **Where the ~6.4 ms/request gap lives** (xdebug cachegrind — instruction totals are
  cross-app INCOMPARABLE, the within-app structure is sound): ~22% phar autoload,
  ~13% filesystem probing (`is_dir`/`is_file` + PathUtil), ~12% route registration
  executed per request, ~5% reflection-based DI. Laravel's `config:cache` /
  `route:cache` / composer authoritative classmap make all four categories ~zero at
  serve time — the architectural cause this epoch could only NAME now has receipts.
- Latency-vs-throughput shape stated honestly: at serial 1-connection the two fpm
  stacks are EQUAL (6.6 ms vs 6.6 ms median, warm) — the 3x gap is a saturated-CPU
  throughput property (queue depth multiplies it into the 244 vs 105 ms averages),
  not a per-request latency difference at low load.

Direction for the framework (SAME WEEK — the owner decided「效能是 RAZY 其中一個
重要的優勢」and compile-on-deploy 全面化 landed): the deploy-time assembly step now
EXISTS — `architecture/COMPILE-ON-DEPLOY.md`: M1 bakes an authoritative classmap at
phar build (kills the autoload FS-probe ladder), M2 compiles the whole declaration
graph per dist (`php Razy.phar compile <dist>`, opt-in via dist.php
`'compiled_boot' => true`), with refusal-on-closures, boot-twice determinism, a
replay self-proof inside the command, and a stat fingerprint that degrades to the
full boot when stale. Until its rate numbers are re-published from clean checked
runs against these very tables, the FPM table remains the honest shape of the
UNCOMPILED trade: Razy pays its assembly at boot, every boot; Laravel pays it once
at deploy. The compiled column earns its row the same way every other row here did.
