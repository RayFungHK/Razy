  framework-vs-framework number; the FPM table plus the gain tables show each

  (4.4× write-bound, 1.8× CPU-bound), Laravel 1.75–3.1× (and 0.5×
  on heavy CPU — frankenphp's threads-vs-processes grain, running honest).

- The worker table is the only framework-vs-framework number: identical PHP,
  identical server, identical runtime policy on both sides.

### Two framework defects this suite caught by existing (both fixed, changelog `[Unreleased]`)

1. **No multisite site could EVER boot under worker mode** — the boot pass has no
   request, HOSTNAME sits at its `'UNKNOWN'` sentinel, and the worker branch fed it to
   `host()` FQDN validation; every thread died and Caddy panicked the pool. The
   standalone path had masked this everywhere. Boot now resolves the sentinel to the
   documented `'*'` default site. Pin: `tests/WorkerBootHostTest.php`.
2. **The `'*'` default site was unreachable by construction** — `matchDomain()` ends with
   a documented `'*'` fallback but `updateSites()` validated every key through `isFqdn()`
   (2+ char label grammar), so `'*'` never entered the table the fallback reads.
   Behavioral fixture: `tests/DefaultSiteTest.php`. (Adjacent doc-trap — the stock
   sites.inc.php comment advertised a string shortcut no parser reads — fixed in the
   setup template the same week.)

The gate suite exists precisely because a gate that is never measured is a gate nobody
trusts; it paid for itself before the first load was even run.


## FPM cold-boot attribution — the OPEN item, CLOSED (2026-09-17)

Method and honest trail first: an xdebug profile pass produced numbers that
CONTRADICTED the published tables (a no-sleep probe showed Razy 7.5k RPS; the
official ramp profile shows 294). The contradiction was chased down instead of
papered over: **xdebug's profile mode writes a cachegrind file per request**, and
that per-request file IO — whose cost scales with the instructions profiled, i.e.
massively asymmetric between the two stacks — invalidated every fpm number taken
while it was on, in BOTH directions. Those probes are named here and shipped as
INVALID; the files were deleted from the containers. With xdebug fully removed
(conf file deleted, pool reloaded):

- **Reproduction:** controlled re-runs of scenario 01 land at Razy 229 / Laravel 850
  (`results/recheck/01_razyfpm_clean.json`, `01_laravelfpm_clean.json`) — the
  published 294.6 / 921 reproduced at the same 0.27x ratio (78–92% level, same
  direction). The published FPM table stands; yesterday's pass was NOT contaminated.
- **The bottleneck is CPU, not queueing** (the two possible causes, now separated).
  CORRECTION, published against myself (the law: invalidated passes are logged
  publicly): the first saturation evidence quoted here — "no-sleep probes: Razy
  9,187 RPS vs Laravel 27,488 → 0.21 vs 0.07 ms CPU/request" — is **INVALID**.
  Those ad-hoc k6 probes ran with `noThresholds` and ZERO checks, so pool-overflow
  502s were counted as `http_reqs`: the RPS was inflated on BOTH sides by an
  unmeasured 502 share, and any ms-CPU/request divided from it inherits the lie.
  The cgroup reading that survives from the same pass is the qualitative one
  (both containers pinned at the 2-core quota — CPU-bound, not queue-bound; that
  holds even in a 502 storm because the CPU is real work either way). The honest
  math comes from the CLEAN CHECKED re-runs above, which plateau at the same
  2-core cgroup quota by the official profile's own design: CPU/request under
  saturation ≈ 2 cores ÷ RPS ⇒ **Razy ≈ 8.7 ms vs Laravel ≈ 2.35 ms**, a ~3.7x
  CPU-cost gap — same direction as the published 0.27x throughput ratio, now
  divided only from numbers that carry checks. (Pools verified symmetric:
  `pm = static`, 32 children, identical `benchmark.ini` both images.)
- **Where the ~6.4 ms/request gap lives** (xdebug cachegrind — instruction totals are
  cross-app INCOMPARABLE, the within-app structure is sound): ~22% phar autoload,
  ~13% filesystem probing (`is_dir`/`is_file` + PathUtil), ~12% route registration
  executed per request, ~5% reflection-based DI. Laravel's `config:cache` /
  `route:cache` / composer authoritative classmap make all four categories ~zero at
  serve time — the architectural cause this epoch could only NAME now has receipts.
- Latency-vs-throughput shape stated honestly: at serial 1-connection the two fpm
  stacks are EQUAL (6.6 ms vs 6.6 ms median, warm) — the 3x gap is a saturated-CPU
  throughput property (queue depth multiplies it into the 244 vs 105 ms averages),
  not a per-request latency difference at low load.

Direction for the framework (SAME WEEK — the owner decided「效能是 RAZY 其中一個
重要的優勢」and compile-on-deploy 全面化 landed): the deploy-time assembly step now
EXISTS — `architecture/COMPILE-ON-DEPLOY.md`: M1 bakes an authoritative classmap at
phar build (kills the autoload FS-probe ladder), M2 compiles the whole declaration
graph per dist (`php Razy.phar compile <dist>`, opt-in via dist.php
`'compiled_boot' => true`), with refusal-on-closures, boot-twice determinism, a
replay self-proof inside the command, and a stat fingerprint that degrades to the
full boot when stale. Until its rate numbers are re-published from clean checked
runs against these very tables, the FPM table remains the honest shape of the
UNCOMPILED trade: Razy pays its assembly at boot, every boot; Laravel pays it once
at deploy. The compiled column earns its row the same way every other row here did.

### The compiled column (published 2026-09-17 — same host/limits/script/pools)

Same-phar A/B on the fpm baseline (scenario 01 + 03, official ramps; `ARG
COMPILED=1` vs `=0` images built from the SAME Razy.phar; one k6 in the compose
network at a time; raw JSONs in `results/recheck/`; `http_req_failed 0` on all
seven passes — the 502-inflation lesson stayed paid):

| pass | RPS | failed | p95 | med |
|---|---|---|---|---|
| 01 legacy (pre-M1 phar = published stack) | 229.1 | 0 | 995.7ms | 216.7ms |
| 01 legacy control (new phar, compiled OFF) | 396.3 | 0 | 593.4ms | 105.1ms |
| 01 legacy control #2 (identical image, re-run) | 198.3 | 0 | 1124.2ms | 251.8ms |
| 01 compiled | 378.4 / 371.0 (×2) | 0 | 589.5 / 612.0ms | 111.8 / 114.3ms |
| 03 legacy control | 230.3 | 0 | 971.3ms | 211.6ms |
| 03 compiled | 239.1 | 0 | 895.2ms | 205.4ms |

Three honest readings, in order of confidence:

1. **The classmap (M1) is the fpm headline: ~+73%.** Every fpm boot pays the
   autoload probe ladder, and M1 removes it with NO opt-in (the map is baked
   into the phar; misses just fall through). 229.1 → 396.3 is that story, and
   it applies to every fpm deployment the moment the phar is rebuilt.
2. **The same-host noise floor is ±2x and this table proves it:** the identical
   control image measured 396.3 then 198.3 across two passes. So the
   compiled passes (371–378) sit INSIDE the control's own band — the defensible
   standing is **"new phar (classmap on) ≈ 370–396 RPS at the 01 plateau"**,
   and no single-pass claim finer than that band survives this measurement.
   Cross-session comparisons (this host vs the published 294.6 pass) must be
   read at the ratio level only, as the 78–92% rule always said.
3. **M2 replay is WITHIN NOISE on this benchmark — stated, not spun.** The fpm
   baseline app is a STANDALONE single module (no scanner walk, one manifest,
   six routes): the replay's savings are tiny and the fingerprint's stat set
   pays roughly what it saves (03: 230.3 vs 239.1; 01: control band contains
   compiled). M2's payoff is where assembly is actually big — multi-site dists
   and worker thread boot (pod start-up / scale-from-zero, where the replay was
   live-verified serving the gate trio) — and this is the first live data
   suggesting the route-registration bucket (12%) only bites with MANY routes:
   six routes is beneath the noise floor. The next compiled-column candidate
   is a multi-module fpm dist (ERP-scale routes) — until then, `compiled_boot`
   stays default-off and this row says so.

### The paired scale instrument (published 2026-09-17 — the instrument finished, and it stung)

The single-pass band above was too coarse to answer M2 at all, so the bench
grew the missing instrument: `benchmark/pair_ab.py` (ARMS ALTERNATE, order
flips per pair, every pass invalidated unless `http_req_failed == 0`) driving a
NEW 60-module multi-site fpm dist (`benchmark/scale/`: greedy dist, one lazy
route per module, scaffold generated IN the image — same anatomy as the gate
scaffold). Same phar, same site, `COMPILED=1/0` build ARG. Raw JSONs:
`results/pair/`.

| comparison (60 modules, 200 VU official ramp, paired) | ratios per pair | median |
|---|---|---|
| compiled (stat fingerprint) / legacy | 0.711 / 0.781 / 0.804 | **0.781** |
| compiled + `RAZY_COMPILE_TRUST=1` (no fingerprint) / legacy | 1.387 / 1.172 / 1.002 | **1.172** |

Three readings, in confidence order:

1. **The fingerprint is the killer, not the replay — mechanism proven inside
   one experiment.** Trust-vs-fingerprint on the SAME artifact flips the arm
   from -22% to +17%: the per-request stat sweep over ~240 files (60 modules'
   worth of manifests/controllers) costs MORE THAN the replay saves — under
   fpm's every-request boot, the safety net became the payload.
2. **Replay itself is a net win at assembly scale, magnitude noisy:** trust ≥
   legacy in every pair (1.002…1.387). The honest claim is "never loses, up to
   +39%, median +17%", not a point number — pairs bought that honesty and the
   pairs also show the residual spread.
3. **Next fix is designed by this data, not by taste:** the fingerprint's
   protection target does not exist in the fpm deployments that would run it —
   with opcache `validate_timestamps=0` (production posture, and this bench's)
   PHP serves FROZEN bytecode, so a hot file edit is already invisible; the
   correct deploy is recompile-in-rebuild, which the fingerprint re-verifies
   for free. The planned change: the fingerprint AUTO-SHORTENS when
   validate_timestamps=0 (documented in the dossier, RZ-reviewed), keeping full
   stats under `=1` (dev, where hot edits are real and throughput is not the
   point). Until that ships: `compiled_boot` on fpm means accepting the
   stat cost or declaring TRUST knowingly.

### The fix ships and is re-measured (same day — 2026-09-17)

The fingerprint now AUTO-SHORTENS when OPcache is genuinely on and
`validate_timestamps` is off (`BootCompiler::fingerprintSkipped()`): under
frozen bytecode the fingerprint's protection target (a hot edit arriving at
boot) does not exist, while dev — opcache off or vt=1, where hot edits are
REAL — keeps the full stats. The first shipping build of the gate measured
UNCHANGED (0.722/0.804/0.771) — because it read `$status['opcache']['enabled']`,
and the STATUS array is FLAT (`opcache_enabled` top-level; the nested tree
belongs to `opcache_get_configuration`). The bug failed SAFE (full stats,
slow-but-correct), and the paired instrument is what caught it — a passing
unit suite without opcache could not. After the key fix, re-measured paired:

| comparison (60 modules, same stacks) | ratios | median |
|---|---|---|
| fingerprint-on (pre-fix) / legacy | 0.722 / 0.804 / 0.771 | 0.771 |
| auto-shorten (shipping) / legacy | 1.418 / 1.230 / 0.958 | **1.230** |
| force-TRUST (earlier hand-controlled run) | 1.387 / 1.172 / 1.002 | 1.172 |

The shipping build now behaves like TRUST **without anyone declaring it**
(distributions agree; medians 1.23 vs 1.17, both noisy within the band).
Honest statement of the claim: compiled fpm at 60-module scale NEVER LOST a
pair once the fingerprint shortened, with the best estimate +17…23% — point
numbers finer than that stay inside this host's resolution. The worker
lane was always the fingerprint-free case (boot once) and stands untouched.

### The shortening's first real enemy — same day, caught by the gate trio

The very next verification (gate trio against the new phar) went down in
flames, and rightly so: the gate image had baked a **dev-machine artifact**
(host `data/compiled/` inside the build context, whose folder keys are
Windows paths). Under the old fingerprint, staleness always caught foreign
artifacts — the stats could never match. **The shortening had silently
lowered the floor to zero**: opcache vt=0 + COPY'd artifact = replay of
paths that cannot exist, boot crash at ModuleInfo, gate never became ready.
The instrument that proves speed also caught what speed-cost the safety net
— same-day, own-stack, published here rather than hidden.

The fix is a STRUCTURE floor that shortening can never skip:
`BootCompiler::originLooksLocal()` — every module folder the snapshot names
must `is_dir` here (a handful of realpath-cached calls, no stat-hashing;
missing structure => `FOREIGN` line, full boot). TRUST shortens the
fingerprint but never the floor (pinned by test). Entry scripts clear the
artifact BEFORE migrate (the first boot is a boot too), and the gate image
now `rm -rf data/compiled` at build — defense in depth against context
bake-in. Re-verified after the floor: gate trio 200/200/503/200 with zero
STALE/FOREIGN lines in the serving window, the worker genuinely serving
from replay (opcache on, vt=0, artifact present), and the paired scale run
on the floor-carrying phar: 1.107 / 0.964 / 1.102, **median 1.102, never
lost a pair** — inside the same +10…+40% noise band as before the floor;
finer than that, this host cannot tell. The floor is not free, it is just
cheaper than what it replaces, and the claim band is unchanged because
nothing inside the band was ever claimable.

### The worker cold-boot lane — measured, and it deflates itself

Worker mode's story was always "boot once, replay earns its keep there".
Said out loud, unmeasured — so the same discipline was applied: 18
intra-container paired runs (fresh 60-module containers, replay-vs-full
order-alternating in the SAME VM per pair). Raw medians said **+7%** for
replay — but the order-slice exposes the artifact: full-first pairs show
+3…16% (second boot = replay = warmer VM), replay-first pairs show
-9…+7%. Warmth, not replay.

Two mechanism probes kept the honesty sharp: (1) a forged FOREIGN artifact
did NOT trigger the FOREIGN line inside a fresh `validate` CLI — CLI
commands run standalone, they never touch the boot snapshot; (2) the
benign positive control (forged FRAMEWORK) proved the compiled path IS
consulted by the real boot — and also caught a real trap: opcache
`validate_timestamps=0` + CLI opcache makes a rewritten artifact invisible
to php-cli for the process's lifetime (the first probes saw stale bytecode;
fresh containers fixed them). And the 40-50ms the sweep measured is
largely CLI process boot — worker's actual initialize sits inside a
~100ms per-request envelope in a frankenphp that boots ONCE per container:
an envelope difference this size is invisible to this instrument by design.

Verdict, published as stated in the law: **the worker replay lane saves
boot milliseconds nobody has to pay twice.** The boot-snapshot stays
honest as an fpm win (+10…+23% steady state, paired) and as a
worker-NEUTRAL option; anyone selling "X-faster cold starts from the
replay" now has this table to answer to. (The throwaway probe scripts are
deleted; the methodology lives here. One general law re-learned, and it is
why EVERY number in this document is order-alternating: the second boot is
always ~15% faster than the first.)
(`results/pair/` holds the LAST measured run in the working tree; every
earlier run — including the fingerprint-on baselines and the hand-TRUST
controls above — is preserved in git history at its commit.)

Instrument cost logged, paying it forward: three build-ARG pairs + one
afternoon went to a proxy-layer hang — a second/third `php_fastcgi` server
block in ONE Caddy container hung in-network requests under Windows Docker
while host probes kept answering (the queue answered, not the app). The pair
arms now run their own single-server nginx per EVIDENCE (`scale/pair.conf.template`);
`Caddyfile.pair` is kept as the dead end's fossil. Ruling out the app layer
(both arms survived 150-VU loads; death only on name-dial paths) is what made
the swap correct rather than guessy.
